The interface has functions to upload files through presigned URLs, create download URLs, write and read files on the server, delete files, check that a file exists, and read its metadata.

## Upload flow

An upload takes two steps:

1. Your server calls `CreateUploadUrl` to generate a presigned upload URL.
2. The client sends the file to the storage provider with that URL.

The file data never reaches your application server, so the server does not pay for its bandwidth.

### Complete upload example

After your server authenticates the caller and authorizes the avatar change, it can issue an upload URL as below. Take `uploadedBy` from the authenticated session. The fixed ID in the example is sample data, not a value to accept from the client.

```ts
import {
  CreateUploadUrl,
  UploadValidationError,
} from "@antelopejs/interface-file-storage";

async function handleUploadRequest(file: {
  name: string;
  size: number;
  type: string;
}) {
  try {
    const response = await CreateUploadUrl(
      {
        filename: file.name,
        size: file.size,
        mimetype: file.type,
        path: "user-uploads/avatars",
        metadata: { uploadedBy: "usr_abc123" },
      },
      {
        maxSize: 5 * 1024 * 1024, // 5 MB
        allowedMimetypes: ["image/jpeg", "image/png", "image/webp"],
      },
    );

    // Return the presigned URL and headers to the client
    return {
      uploadUrl: response.uploadUrl,
      resourceKey: response.resourceKey,
      headers: response.headers,
      expiresAt: response.expiresAt,
    };
  } catch (error) {
    if (error instanceof UploadValidationError) {
      throw new Error(`Upload rejected: ${error.message}`);
    }
    throw error;
  }
}
```

The client then uploads the file with the presigned URL:

```ts
// Client-side upload using the response from the server
async function uploadFile(
  file: File,
  presignedData: { uploadUrl: string; headers: Record<string, string> },
) {
  const response = await fetch(presignedData.uploadUrl, {
    method: "PUT",
    headers: presignedData.headers,
    body: file,
  });

  if (!response.ok) {
    throw new Error("Upload failed");
  }
}
```

The client must send every header from the `headers` field with the PUT request. The presigned URL signature covers `Content-Type` and `Content-Length`, so the storage rejects a request that changes either value.

Each upload gets a fresh key, and the storage accepts it only if no object exists there yet. Replaying a URL must not overwrite an accepted object. A concurrent or repeated attempt gets an explicit conflict answer. The exact answer is provider behaviour: `@antelopejs/file-storage-local` answers HTTP 409, and `@antelopejs/file-storage-s3` returns an `If-None-Match: *` header, so S3 rejects a write to a key that already holds an object. To upload again, request a fresh upload URL. Forward every returned header, `If-None-Match` included when the response has it, and allow those headers in the storage CORS policy. The provider must enforce the condition, not only return the header.

The create-only rule does not reserve a deleted key forever. An upload URL that has not expired yet can recreate a deleted source, so your application's admission step must not reuse the original upload key. Staging expiration and source cleanup do not depend on business cancellation.

### The `UploadRequest` object

The upload example accepts these fields:

| Field        | Type                     | Required | Description                                                                                      |
| ------------ | ------------------------ | -------- | ------------------------------------------------------------------------------------------------ |
| `filename`   | `string`                 | Yes      | Original filename                                                                                |
| `size`       | `number`                 | Yes      | Exact file size in bytes                                                                         |
| `mimetype`   | `string`                 | Yes      | MIME type, such as `"image/jpeg"`                                                                |
| `path`       | `string`                 | No       | Folder for the file. The provider decides how it appears in the key                              |
| `metadata`   | `Record<string, string>` | No       | Custom file metadata                                                                             |
| `visibility` | `"public" \| "private"`  | No       | Override the storage default                                                                     |
| `staging`    | `boolean`                | No       | Upload to temporary staging, `false` by default. See [promotion](#staging-uploads-and-promotion) |

### The `UploadConstraints` object

The provider checks the request against the constraints before it generates a URL. A request that fails throws `UploadValidationError`. This check reads only the request, not the file content, so validate the final object before you attach it to an application record.

| Field              | Type       | Description                |
| ------------------ | ---------- | -------------------------- |
| `maxSize`          | `number`   | Maximum file size in bytes |
| `allowedMimetypes` | `string[]` | Permitted MIME types       |

### The `PresignedUploadResponse` object

| Field         | Type                     | Description                        |
| ------------- | ------------------------ | ---------------------------------- |
| `uploadUrl`   | `string`                 | URL for the client's PUT request   |
| `resourceKey` | `string`                 | Key to retain for later operations |
| `expiresAt`   | `number`                 | Upload URL expiration timestamp    |
| `headers`     | `Record<string, string>` | Required PUT headers               |

## Write a file from the server

A module that produces files itself, such as generated derivatives or seeded content, stores them with `WriteFile` instead of uploading to its own presigned URL. The file gets the key, metadata, visibility, and staging that an upload of the same request would get. `WriteFile` never writes over an existing object. It makes no HTTP round trip, so it works before the API server listens.

```typescript
import { WriteFile } from "@antelopejs/interface-file-storage";

async function storeThumbnail(bytes: Uint8Array) {
  const { resourceKey } = await WriteFile(
    {
      filename: "thumb.webp",
      size: bytes.byteLength,
      mimetype: "image/webp",
      path: "media/thumbs",
    },
    bytes,
  );
  return resourceKey;
}
```

`size` must equal `bytes.byteLength`. Otherwise `WriteFile` throws `UploadValidationError`. The interface does not fix the error code for this case. Both `@antelopejs/file-storage-local` and `@antelopejs/file-storage-s3` use `SIZE_EXCEEDED`.

## Staging uploads and promotion

A file uploaded through a presigned URL is in storage as soon as the upload ends. If the user never confirms the form, nothing references the key, and the object stays in storage with no owner.

Staging handles that case. Set `staging: true` on the upload request, and the generated `resourceKey` starts with the reserved staging prefix, `STAGING_PREFIX` (`"__staging__/"`). The rest of the key is provider behaviour:

```ts
import { CreateUploadUrl } from "@antelopejs/interface-file-storage";

const upload = await CreateUploadUrl({
  filename: "draft.png",
  size: 204800,
  mimetype: "image/png",
  path: "user-uploads/avatars",
  visibility: "private",
  staging: true,
});

console.log(upload.resourceKey); // starts with "__staging__/"
```

- `@antelopejs/file-storage-local` gives `__staging__/user-uploads/avatars/<uuid>.png` for this request.
- `@antelopejs/file-storage-s3` adds a visibility segment when the request sets `visibility`, which gives `__staging__/__visibility__/private/user-uploads/avatars/<uuid>.png`.

When you configure staging expiration, the backend expires abandoned objects with an S3 lifecycle rule or a periodic local sweep. Staging alone does not turn on cleanup. See [backend expiration of staged files](#backend-expiration-of-staged-files).

### Staging key helpers

These public helpers work on strings only. They do not check that a file exists, authorize access, or upload, move, or promote a file. They take no `storage` argument.

| Export                                            | Behavior                                                        |
| ------------------------------------------------- | --------------------------------------------------------------- |
| `STAGING_PREFIX`                                  | The reserved prefix `"__staging__/"`.                           |
| `isStagedKey(resourceKey: string): boolean`       | Tests whether the key begins with the prefix.                   |
| `toStagedKey(resourceKey: string): string`        | Adds the prefix unless it is already present.                   |
| `stripStagingPrefix(resourceKey: string): string` | Removes one leading prefix. Returns a non-staged key unchanged. |

```ts
import {
  isStagedKey,
  toStagedKey,
  stripStagingPrefix,
} from "@antelopejs/interface-file-storage";

const staged = toStagedKey("avatars/photo.png");
console.log(staged); // "__staging__/avatars/photo.png"
console.log(isStagedKey(staged)); // true
console.log(toStagedKey(staged)); // unchanged
console.log(stripStagingPrefix(staged)); // "avatars/photo.png"
console.log(stripStagingPrefix("avatars/photo.png")); // unchanged
```

To publish a confirmed upload, use `PromoteFile`, described in the next section. A final key computed with `stripStagingPrefix` does not prove that a promotion succeeded.

### Promoting a confirmed file

Before you admit a file into the record that references it, call `PromoteFile` with its staged key. The provider strips the staging prefix. It then publishes the complete bytes, the metadata, and the trusted source provenance at the final key, and it never overwrites an existing destination. The file keeps its visibility and stays in the same storage. The provider removes the source only after it verifies the final publication.

```ts
import { PromoteFile } from "@antelopejs/interface-file-storage";

const { resourceKey } = await PromoteFile(
  "__staging__/user-uploads/avatars/<uuid>.png",
);
console.log(resourceKey); // "user-uploads/avatars/<uuid>.png"
```

You can call `PromoteFile` again with the same key. The results are:

- A key that is not staged comes back unchanged, and nothing moves.
- A second promotion of the same staged key returns the final key again only when the destination is complete and its trusted provenance matches that source. A retry after the source was removed works the same way.
- If the staged object no longer exists and was never promoted, `PromoteFile` throws `FileNotFoundError` instead of returning a key that points to nothing. An object that expired before promotion is one such case.
- A foreign destination, or an incomplete destination that the provider cannot verify, throws `FileConflictError` with code `"FILE_CONFLICT"`. An existing object, an equal size, or metadata from the upload does not prove a matching promotion.
- An unknown provider outcome throws. To settle it, retry with the same key and storage. Never treat an error or an existence check as proof of success.

### Provider and application responsibilities

Application authors enforce the admission and access rules below. Backend authors also implement the [provider promotion contract](./3.provider-contract.md). `PromoteFile` has no fallback to `MoveFile` plus `FileExists`.

#### Publish a complete object

If you implement a storage backend, follow the [requirements for a complete publication](./3.provider-contract.md#publish-a-complete-object). Application authors can skip to admission and access below.

#### Admit the file into application data

Your application stores who owns the source, and checks the final metadata after promotion, before it commits the business admission. Use the same storage for the upload, the promotion, the validation, the reads, and the cleanup. Do not switch to another backend partway through.

Cancellation and receipts belong to your application. Storage has no cancellation marker or fence, so delayed work can leave an orphan after a cancellation. Never attach that orphan to a cancelled admission.

#### Protect private files

For a private workflow, the server sets `visibility: "private"` in its trusted upload authorization, and the client cannot change it. Providers enforce private access to both the staged and the final bytes. Signed URLs over storage that anyone can read do not make a file private.

Your application also authorizes its metadata and read-URL routes against the business admission. Private storage alone does not stop a permissive application route from handing out a read URL to the wrong caller. A read URL that was already issued keeps working until it expires.

### Moving an object

`MoveFile` is a generic move, separate from promotion. A missing source is a no-op. The interface leaves overwrites to the provider. Both `@antelopejs/file-storage-local` and `@antelopejs/file-storage-s3` overwrite an existing destination. It does not replace promotion, which never overwrites, and `PromoteFile` does not call it.

```ts
import { MoveFile } from "@antelopejs/interface-file-storage";

await MoveFile("reports/draft.pdf", "reports/review.pdf");
```

### Backend expiration of staged files

Each implementation expires abandoned staged objects in its own way:

- `@antelopejs/file-storage-s3`: set `stagingExpirationDays` on a storage config. When the module starts, it applies a bucket lifecycle rule limited to the staging prefix. If that fails, the module logs a warning and starts anyway. To manage the bucket as external infrastructure, leave the field unset and create an equivalent lifecycle rule with Terraform or the console.
- `@antelopejs/file-storage-local`: set `stagingExpiration`, in seconds. The periodic cleanup then deletes staged files older than that age. Without it, staged files stay forever, which suits development only.

## Download flow

`CreateReadUrl` generates a URL to a stored file.

### The `PresignedReadResponse` object

| Field       | Type               | Description                                   |
| ----------- | ------------------ | --------------------------------------------- |
| `url`       | `string`           | URL to access the file                        |
| `expiresAt` | `number`, optional | Expiration timestamp, absent for public files |

### Generate a download URL

```ts
import { CreateReadUrl } from "@antelopejs/interface-file-storage";

// Generate a read URL with 1-hour expiration (for private files)
const { url, expiresAt } = await CreateReadUrl(
  "user-uploads/avatars/photo.jpg",
  3600,
);

console.log(url); // Presigned or public URL
console.log(expiresAt); // Expiration timestamp, or undefined if public
```

### Serve files in an API response

```ts
import { CreateReadUrl } from "@antelopejs/interface-file-storage";

async function getFileDownloadUrl(resourceKey: string) {
  const { url, expiresAt } = await CreateReadUrl(resourceKey, 300); // 5 minutes

  return {
    downloadUrl: url,
    expiresAt,
  };
}
```

## Read a file from the server

When the server itself needs the bytes, read them with `ReadFile` instead of a read URL. Examples are probing an image, generating a derivative, or streaming a file through an API route. A read URL carries the storage's public address, which a backend behind a private network or an egress policy cannot reach. `ReadFile` makes no HTTP round trip and does not check visibility, so the caller must authorize the read.

```typescript
import { buffer } from "node:stream/consumers";
import { ReadFile } from "@antelopejs/interface-file-storage";

const { body, size, mimetype } = await ReadFile("media/photos/abc.png");
const bytes = await buffer(body);
```

`body` is a Node.js `Readable`. Pipe it to stream a large file, and destroy it to stop reading early. A missing file throws `FileNotFoundError`.

## Delete a file

`DeleteFile` removes a file from storage.

```ts
import { DeleteFile } from "@antelopejs/interface-file-storage";

await DeleteFile("user-uploads/avatars/old-photo.jpg");
```

To delete a file from a specific storage bucket:

```ts
import { DeleteFile } from "@antelopejs/interface-file-storage";

await DeleteFile("backups/archive-2025.zip", "backup-bucket");
```

## Check file existence

`FileExists` resolves to `true` if the file exists and `false` otherwise.

```ts
import { FileExists } from "@antelopejs/interface-file-storage";

const exists = await FileExists("user-uploads/avatars/photo.jpg");

if (!exists) {
  console.log("File not found, using default avatar.");
}
```

## File metadata

`GetFileMetadata` reads the metadata of a stored file. It throws `FileNotFoundError` if the file does not exist.

### The `FileMetadata` object

| Field          | Type                               | Description                          |
| -------------- | ---------------------------------- | ------------------------------------ |
| `resourceKey`  | `string`                           | Unique resource key                  |
| `filename`     | `string`                           | Original filename                    |
| `size`         | `number`                           | File size in bytes                   |
| `mimetype`     | `string`                           | MIME type                            |
| `lastModified` | `number`                           | Last modified timestamp              |
| `metadata`     | `Record<string, string>`, optional | Custom metadata attached to the file |

### Retrieve file metadata

```ts
import {
  GetFileMetadata,
  FileNotFoundError,
} from "@antelopejs/interface-file-storage";

try {
  const meta = await GetFileMetadata("user-uploads/avatars/photo.jpg");

  console.log(meta.filename); // "photo.jpg"
  console.log(meta.size); // 204800
  console.log(meta.mimetype); // "image/jpeg"
  console.log(meta.lastModified); // 1711800000000
  console.log(meta.metadata); // { uploadedBy: "usr_abc123" }
} catch (error) {
  if (error instanceof FileNotFoundError) {
    console.error("The requested file does not exist.");
  }
}
```

## Complete workflow example

Run this example in a server-side test, with a configured storage implementation and the built-in `fetch`. It uploads a small text report, reads its metadata, and deletes it. In a browser flow, the client runs the PUT instead. Requesting a URL alone never creates the object. A staged workflow also needs promotion and application admission before any read.

```ts
import {
  CreateUploadUrl,
  CreateReadUrl,
  GetFileMetadata,
  DeleteFile,
  FileExists,
} from "@antelopejs/interface-file-storage";

const bytes = Buffer.from("Quarterly report\nRevenue: 12500 EUR\n", "utf8");

// 1. Generate a presigned upload URL for these exact bytes.
const upload = await CreateUploadUrl({
  filename: "report.txt",
  size: bytes.length,
  mimetype: "text/plain",
  path: "reports/2026",
  visibility: "private",
});

// 2. Upload before trying to read the object.
const uploaded = await fetch(upload.uploadUrl, {
  method: "PUT",
  headers: upload.headers,
  body: bytes,
});
if (!uploaded.ok) {
  throw new Error(`Upload failed: ${uploaded.status}`);
}

// 3. After a successful upload, generate a read URL.
const read = await CreateReadUrl(upload.resourceKey, 3600);
console.log("Read URL expires at:", read.expiresAt);

// 4. Retrieve metadata.
const metadata = await GetFileMetadata(upload.resourceKey);
console.log("File size:", metadata.size, "bytes");

// 5. Check existence before deleting this disposable file.
const exists = await FileExists(upload.resourceKey);
if (exists) {
  await DeleteFile(upload.resourceKey);
  console.log("File deleted.");
}
```
