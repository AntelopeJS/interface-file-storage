# Immutable file seals

The additive seal API binds attachment admission to one immutable upload generation. It does not change `MoveFile` or `PromoteFile`, and callers must not fall back to those APIs when sealing fails. A backend must implement this contract before a caller removes coordination that previously protected attachment promotion.

## Persist the complete admission before sealing

Call `GetFileSnapshot(resourceKey, storage?)` to obtain `FileSnapshot`: an `identity` containing `storageId`, `resourceKey`, and `generation`, together with metadata for those exact bytes. The backing-store identity survives restarts and alias changes, but changes when the backing store changes. A generation identifies an immutable upload occurrence, including identical-byte PUT replays; a content hash, ETag, size, or modification timestamp alone is insufficient.

Persist a `SealFileRequest` containing that identity as `source`, a `destinationKey`, and an `admissionId`. The admission ID is unique within the backing store and permanently binds the entire request. Reusing it with any changed field fails with `DESTINATION_CONFLICT`, including after removal. Empty identifiers, identical source and destination keys, and backend-invalid keys fail with `INVALID_REQUEST`. Resolving the supplied storage alias to a different backing store fails with `STORAGE_MISMATCH` before any writes.

The caller admits the stable source key once, retains that admission permanently, and uses the same tuple for every retry. Storage provenance is backend-authenticated state, not upload-controlled custom metadata. The adapter reserves its internal state and byte keys from ordinary uploads, moves, and deletes.

`destinationKey` must contain a nonempty suffix under `SEALED_PREFIX` (`__sealed__/`). This namespace is reserved for logical sealed destinations; ordinary upload, move, and delete operations must reject it rather than bypass admission state. Legacy APIs remain unchanged for ordinary keys. Backend-private byte and state namespaces are separate implementation details.

## Seal copies bytes without deleting the source

`SealFile(request, storage?)` returns `SealedFile`: the destination identity, matching metadata, and provenance containing `admissionId` and `source`. It publishes only the expected source generation and never deletes the source. A backend may use a retained immutable version after a newer upload, or reject with `GENERATION_MISMATCH`; it must never substitute the newer bytes. A missing, unretained source fails with `FileNotFoundError` before the first commit.

A destination already owned by exactly this request returns the original committed destination identity, even if the source subsequently disappears. A different owner, changed request, replaced destination, or missing ownership proof fails closed with `DESTINATION_CONFLICT`. The original destination is not overwritten. Concurrent matching seals converge on the same committed identity, not just equal bytes.

## Removal permanently fences publication

`GetFileSeal(request, storage?)` returns one of these durable states:

| State                                    | Meaning                                                                    |
| ---------------------------------------- | -------------------------------------------------------------------------- |
| `{ status: "absent" }`                   | No admission decision exists yet. An in-flight operation may still commit. |
| `{ status: "sealed", file: SealedFile }` | The exact destination generation and provenance are committed.             |
| `{ status: "removed" }`                  | The admission is terminally cancelled and cannot publish again.            |

`RemoveSealedFile(request, storage?)` permanently transitions an absent or sealed admission to removed. The tombstone binds the entire tuple and survives restarts; neither a retry nor a delayed seal may replace it. A later `SealFile` fails with `ADMISSION_REMOVED`. Repeated removal succeeds. A removal never deletes a replacement or another admission's destination; conflicting ownership fails closed and retains any cancellation fence already committed.

Removal success means logical absence and a durable publication fence, not immediate physical erasure. Private orphan bytes may await garbage collection. All read, metadata, existence, and legacy mutation operations on sealed logical keys must honor the seal state and preserve its fence. Internal byte objects must not have public raw URLs; already-issued signed read capabilities may remain valid until expiration. This contract does not promise retroactive URL revocation or redesign access controls for ordinary files.

## Publish one decision atomically

A feasible implementation writes immutable private bytes first and conditionally publishes a complete logical slot containing their generation, metadata, and provenance. Removal conditionally replaces that same slot with a terminal tombstone. Admission-ID binding also needs durable coordination; allocating a separate marker does not make an unconditional destination write safe.

An immutable admission-to-request record can reserve the complete tuple with create-if-absent before any destination publication or removal. This record never changes and does not control cancellation; only the destination slot does. A crash after binding but before publication leaves an absent publication decision, and a matching retry resumes safely. A changed tuple conflicts with the binding. `GetFileSeal` must also reject an occupied foreign or unverifiable destination with `DESTINATION_CONFLICT`, even when no record exists for the requested admission.

If removal wins before publication, a delayed seal's conditional publication fails against the tombstone. If sealing wins first, removal replaces the exact sealed slot, and later replay observes removed. If a writer crashes after preparing bytes but before publication, the bytes remain private orphans. If publication commits but the response is lost, reading the slot recovers the same destination identity. Conditional state updates must include a unique state revision in the protected value; a provider ETag that excludes metadata cannot fence revisions stored only in metadata.

Local implementations must durably prepare complete metadata and bytes before publication, synchronize the required files and directories, and repair partial work before serving reads after restart. Renaming bytes and subsequently writing metadata without a recovery record does not satisfy the contract. An implementation restricted to one writer process must document and enforce that deployment boundary; ephemeral serialization does not coordinate independent processes.

## Reconcile unknown outcomes without inventing success

`FileSealError` exposes a `code`: `UNSUPPORTED`, `STORAGE_MISMATCH`, `GENERATION_MISMATCH`, `DESTINATION_CONFLICT`, `OUTCOME_UNKNOWN`, `INVALID_REQUEST`, or `ADMISSION_REMOVED`. Providers must report `UNSUPPORTED` before unsafe writes when their configuration lacks the required primitives. An unavailable provider, timeout, or crash is not proof that nothing committed.

After `OUTCOME_UNKNOWN`, call `GetFileSeal` with the same persisted request. Sealed recovers the committed result, removed proves terminal cancellation, and absent permits a same-request retry but does not cancel an in-flight operation. To abort, retry `RemoveSealedFile` until its outcome is known. Incomplete or unverifiable durable work produces `OUTCOME_UNKNOWN` or a conflict until repaired, never a fabricated absent or sealed result. Only a completed terminal state returns removed; a cancellation fence awaiting reconciliation may still report `OUTCOME_UNKNOWN`.

This is an idempotent logical publication contract, not an exactly-once provider I/O guarantee. Provider retries can create private orphan versions, and garbage collection must conditionally target only recorded owned generations. Staging lifecycle expiry remains independent; sealed bytes must not inherit staging expiry.

## Verification responsibilities

`pnpm test` verifies public forwarding, error propagation, and legacy compatibility. `test/seal-conformance.mjs` supplies reusable backend scenarios through a disposable fixture; adapter repositories must run those scenarios or equivalent tests against their implementations. Interface forwarding tests do not prove provider atomicity.

Adapters also need deterministic fault injection: pause seal immediately before publication, remove, then resume; crash after byte preparation and after publication; lose successful responses; race distinct admissions for a destination; replace an owned generation before cleanup; restart after a tombstone; replay an upload URL with identical bytes; and attempt public/raw reads of orphan bytes. State, bytes, metadata, and identity must all be checked, not merely the absence of exceptions.
